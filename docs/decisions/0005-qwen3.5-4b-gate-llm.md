# ADR-0005: qwen3.5:4b via Ollama for the gate

- **Status:** Accepted
- **Date:** 2026-05-20 (backfilled)
- **Related:** ADR-0001

## Context

The gate (`docs/2026-05-16-…-design.md`, section 4) is a fast LLM that decides
whether an accumulated ASR transcript is a *complete thought*. It fires on
every endpointed pause, so it sits in the user-perceived latency budget:

- **Latency target**: ~300 ms or better on a warm request. The gate runs after
  endpointing and before submit; any time spent here delays the assistant.
- **Accuracy target**: high recall on completeness; the design accepts that the
  prompt tells the model to err toward `prompt` when unsure.
- **Determinism**: the response must be valid JSON, every time.
- **Cost**: free and local is preferred — the gate fires constantly.
- **Hardware**: must coexist with other workloads on a 3060 Ti (8 GB VRAM).

A formal bake-off was run; see `eval/` and the table in `eval/results.csv`.

## Decision

Use **`qwen3.5:4b`** (Q4_K_M, ~3.4 GB GGUF) served by **Ollama** on
`http://localhost:11434/v1/chat/completions` via the OpenAI-compatible API.
Configured as the default in `src/config.rs`.

Eval result (88 cases, 3 runs, n=264):

```
total_median_ms 276   total_p95_ms 341   total_max_ms 576
accuracy 0.841   hold_accuracy 0.548
```

## Consequences

- Comfortably under the 300 ms median target; p95 is 341 ms; max ~580 ms.
- VRAM cost is real: ~6.2 GB resident with the default 4096-token context,
  leaving ~1.8 GB headroom on a 3060 Ti. Context can be reduced (see Notes)
  since gate calls are stateless and short.
- Ollama lazily reloads the model after 5 minutes of idle; the first call
  after eviction pays a ~2-4 s cold load. Mitigation: prewarm at startup
  and/or send `keep_alive: -1`.
- Failure mode is graceful: `Gate::classify` fails open to `Verdict::Prompt`
  on any error or timeout (`src/gate.rs:122`, design 4.7). Outages degrade
  to "submit every utterance", not "voice loop hangs".

## Alternatives considered

From `eval/results.csv` (same dataset; 88 cases, 3 runs):

| Candidate | total median (ms) | accuracy | Reason it lost |
|---|---|---|---|
| `qwen3:1.7b` (ollama) | 104 | 0.447 | Half the accuracy. Speed not worth it. |
| `qwen3:0.6b` (ollama) | 111 | 0.473 | Same — too small to judge completeness. |
| `gemma3:4b` (ollama) | 241 | 0.648 | Slower and notably less accurate. |
| `granite3.3:8b` (ollama) | 131 | 0.625 | Faster, but loses 22 pts of accuracy. |
| `gemma3:270m` (ollama) | 640 | 0.364 | Slow *and* inaccurate at this task. |
| `qwen3.5-4b` via llama.cpp (V3/V4 tight) | 108 | 0.848 | Best speed/accuracy point. Lost on integration cost: Ollama is one HTTP call and the model registry is shared; llama.cpp wants direct embedding (`llama-cpp-2`) or its own server. Revisit if the daemon becomes a problem. |
| `deepseek-v4-flash` (cloud, no-think) | 821 | 0.852 | 3× slower and cloud-bound. |
| `gpt-oss-120b` (Cerebras) | 102 | 0.83 | Lower accuracy than the local 4B; cloud-bound. |

## Notes

- Cold-load behaviour: a fresh first request can take 2-4 s while Ollama
  pages weights in. Steady-state warm requests are ~270 ms (measured
  2026-05-20).
- Default `num_ctx` is 4096 but the gate sends ≤~500 tokens per call. Reducing
  context to 1024 saves roughly 0.8-1.2 GB VRAM with no quality impact and is
  worth doing if we add a second resident model.
